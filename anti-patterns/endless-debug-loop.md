# Endless Debug Loop（无限调试循环）

> 反模式：改 A 坏 B，改 B 坏 A，无限循环——只治症状，不治根因。

## Bad Approach

Bug 出现，让 AI 直接"修一下"，改完发现别的地方坏了，再让它修那个，又把原来的改回来……来回打补丁。常见表现：

- 不复现、不定位，直接让 AI 改
- 改一堆地方看哪个碰巧好
- 改完只看原报错没了，不验别处
- 越改越乱，最后谁也说不清改了啥

## Why It Looks Reasonable

- "AI 改 Bug 很快，试几轮总能碰中"——感觉比花时间定位根因更高效。
- 每改一处只看眼前报错，感觉在推进，其实是在兜圈。
- 如果碰巧第一轮就修好了，会强化"直接让 AI 试"的习惯。

## Why It Fails

- **只治症状不治根因**：报错是表象，根因（真正导致 Bug 的原因）没找。盖住报错，Bug 换个姿势回来。
- **改动面越滚越大**：每次打补丁都在加复杂度，新补丁和旧补丁互相冲突。
- **违反原则 07（宪法第 7 条）** Every bug needs a reproducible cause——每个 Bug 都要可复现的根因。

靠猜改 Bug，本质是赌运气，赌不中就无限循环。

## Better Approach

用 systematic-debugging 的 6 步找根因：

1. **稳定复现**：先找到一组必现的操作步骤。时有时无的 Bug 没法验证修没修好。
2. **缩到最小用例**：砍掉无关操作，留下最少的一组复现步骤。
3. **二分定位**：在嫌疑范围内注释/回退一半，看 Bug 还在不在，逐步收窄。
4. **找根因**：找到真正导致 Bug 的原因，不是报错信息本身。
5. **最小修复**：只改导致根因的那一处，不连带改别的。
6. **回归验证**：跑原用例确认不再复现，再跑相关测试确认没改坏别处。

## Example

Bug：分页列表第 2 页显示成第 1 页的数据。

❌ 无限循环：

```
AI：我把页码参数改大了。
→ 列表第 1 页又显示成第 2 页的了。
AI：那我加个判断。
→ 筛选又坏了。
AI：那我再调一下……
（三轮回合，越来越乱）
```

✅ 系统化 6 步：

```
1. 复现：每次点第 2 页都必现 ✅
2. 最小用例：只点"第 2 页"，不筛选 ✅
3. 二分：后端返回数据正确 → 锁定前端传参
4. 根因：前端传 page 时用了 pageSize 当 page
5. 最小修复：只改这一处传参
6. 回归：第 2 页✅ 筛选✅ 相关测试全过✅
```

一次定位根因，改一处，彻底解决。

## Prevention

- 改 Bug 前先稳定复现，复现不了就先不改。
- 改完一处立刻跑回归测试，不只看原报错消失。
- **超过 3 轮还没修好就停**——回 [systematic-debugging](../skills/core/systematic-debugging/SKILL.md) 的 6 步走根因。
