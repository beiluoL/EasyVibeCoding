# Requirements — 多租户 AI SaaS 平台 MVP

> ⚠️ Verification Pending — 需求清单已就位，但功能尚未实际实现验证。

## 功能性需求（FR）

| 编号 | 需求描述 | 优先级 | 验收标准 |
| --- | --- | --- | --- |
| FR-01 | 租户管理员能注册新租户并创建首个账号 | P0 | 注册成功生成租户 ID 与管理员账号，可登录 |
| FR-02 | 用户能用账号密码登录，登录态绑定租户 | P0 | 登录后拿到 Token，后续请求带租户 ID |
| FR-03 | 租户数据相互隔离：A 看不到 B 的文档与对话 | P0 | A 上传文档后，B 提问检索不到 A 的内容 |
| FR-04 | 租户内成员能上传文档进自家知识库 | P0 | 上传后文档仅进入本租户 collection |
| FR-05 | 租户内成员能针对自家文档问答 | P0 | 提问得到基于本租户文档的回答与引用 |
| FR-06 | 平台能统计各租户用量（调用次数/Token） | P1 | 每次问答后用量计数 +1，可按租户查累计 |

> 术语解释：**FR（功能性需求）**= 产品"能做什么"；**P0** = 必须有，没有就不算交付。**租户 ID** = 给每家公司发的唯一编号，所有数据都按它分柜存放。

## 非功能性需求（NFR）

| 编号 | 需求描述 | 优先级 | 验收标准 |
| --- | --- | --- | --- |
| NFR-01 | 租户数据隔离：应用层用租户 ID 强制过滤，单点失误不致泄露 | P0 | 任意接口默认带租户过滤；伪造/缺失租户 ID 请求被拒 |
| NFR-02 | 密钥（LLM/Embedding Key）绝不入库、不上前端 | P0 | 全仓库 grep 不到真实 key；前端无硬编码 key |
| NFR-03 | 计费为 stub：只累加用量数字，不接真实支付 | P0 | 计费模块无对外支付请求；只写本地计数器 |
| NFR-04 | 请求超时要有兜底（默认 30s） | P1 | LLM 超时显示"请求超时"，不串租户不卡死 |
| NFR-05 | 隔离边界可审计：关键路径有租户 ID 日志 | P1 | 日志可见请求归属租户，便于事后排查 |

> ⚠️ NFR-01 的"单点失误不致泄露"为目标，未做安全审计实测。

## 验收标准（Acceptance Criteria）

端到端验收（全部通过才算交付）：

1. 注册租户 A 与租户 B，各自登录
2. A 上传一份文档入知识库，B 上传另一份
3. A 提问 A 的文档内容，答对且引用 A 的出处
4. B 提问 A 的文档内容，应检索不到、答"未覆盖"而非泄露
5. A、B 各自用量计数随问答累加，互不影响
6. 未登录 / 伪造租户 ID 请求被拒
7. 断网 / 超限 / key 失效时显示可读错误，不串租户
8. 全仓库搜不到真实 API Key

> 以上均为 Expected Verification Steps，尚未实际执行。详见 [verification.md](verification.md)。

## 不做（Out of Scope）

- 真实支付对接（计费仅 stub）
- 组织内成员分级权限（租户内等权）
- 流式输出
- 多模型路由 / 负载均衡
- SLA 监控与告警
- 公网部署
