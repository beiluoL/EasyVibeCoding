# Scoring Framework V0.1 — 8 维度评分标准

> ⚠️ Not Yet Verified — 本文件仅提供评分框架定义。V0.1 尚无真实模型跑分数据，所有分值待 V0.2 真实执行后填入。

## 框架说明

每个 Benchmark 任务在验收后，都会在以下 8 个维度上得到一个 **0 ~ 10 的整数分**，然后按加权公式算总分。

这 8 个维度的中文名 + 大白话解释：

| 维度 | 英文名 | 大白话解释 |
|:---:|:---|:---|
| 1 | **Correctness** | **正确性** — 功能到底对不对、需求有没有"做出来" |
| 2 | **Test Pass Rate** | **测试通过率** — 任务自带或 AI 自写的测试，跑通过了几条 |
| 3 | **Code Quality** | **代码质量** — 命名、结构、注释、有没有明显反模式 |
| 4 | **Security** | **安全性** — 有没有 SQL 注入 / 密钥泄露 / 越权 等问题 |
| 5 | **Maintainability** | **可维护性** — 后面别人改这段代码会不会想死 |
| 6 | **Token Usage** | **Token 消耗** — 完成同样任务，AI 花了多少 Token（越少越好） |
| 7 | **Latency** | **耗时** — 从发请求到验收通过花了多少秒（越快越好） |
| 8 | **Human Intervention** | **人工干预度** — AI 自己搞定了多少，要不要人类反复擦屁股 |

---

## 0-10 分细则（每个维度一张表）

### 1. Correctness（正确性）

| 分数 | 判定标准 |
|:---:|:---|
| 0 | 功能完全没做出来，或产物根本跑不起来 |
| 1–2 | 只做了 10%~20% 的核心功能，其余完全缺失 |
| 3–4 | 做了一部分，但核心 happy path（正常路径）仍有明显缺口 |
| 5–6 | Happy path 基本可用，但边界/错误场景大面积缺失 |
| 7–8 | Happy path + 主要边界场景都对，只有极个别 AC（验收条件）没过 |
| 9 | 所有可客观判定的 AC 全过，只在非常极端的 case 有瑕疵 |
| 10 | 100% 达到或超过任务 Goal，没有任何客观验收项未通过 |

### 2. Test Pass Rate（测试通过率）

> 注：以「任务 Acceptance Criteria 对应的自动化测试用例」为分母。若任务要求 AI 写测试（如 B09），则同时计算 AI 写的测试被执行的通过率。

| 分数 | 判定标准 |
|:---:|:---|
| 0 | 0% 通过，或根本没有可运行的测试 |
| 1–2 | ≤ 20% 通过 |
| 3–4 | 21% ~ 40% 通过 |
| 5–6 | 41% ~ 60% 通过 |
| 7–8 | 61% ~ 85% 通过 |
| 9 | 86% ~ 99% 通过，仅 1~2 条非核心用例失败 |
| 10 | 100% 全通过 |

### 3. Code Quality（代码质量）

| 分数 | 判定标准 |
|:---:|:---|
| 0 | 代码不可读，变量名全是 `a/b/c`，格式混乱 |
| 1–2 | 极度不规范，到处是复制粘贴死代码、无注释、命名反直觉 |
| 3–4 | 有基本命名，但结构混乱、文件/函数职责不清 |
| 5–6 | 基本规范，能看懂，但存在明显冗余、缺乏一致风格 |
| 7–8 | 命名清晰、结构合理，符合项目约定，少量可优化点 |
| 9 | 风格统一，职责单一，关键位置有注释，无明显坏味道 |
| 10 | 教科书级别，干净、简洁、表达意图比"人类自己写的"还清楚 |

### 4. Security（安全性）

| 分数 | 判定标准 |
|:---:|:---|
| 0 | 存在 ≥1 个 **blocker** 级漏洞（SQLi/RCE/前端硬编码 AK 等）且未处理 |
| 1–2 | 多个高危问题并存，基本等于"裸奔" |
| 3–4 | 修了一个最致命的，但还留着其他中高危 |
| 5–6 | 没有明显 blocker，但缺少输入校验/鉴权细节等基本防线 |
| 7–8 | 常见问题都处理了（SQLi / XSS / authz / key 保护），只有边角问题 |
| 9 | 安全防线完整，遵循最小权限，边界清晰，只有极微小的 nit |
| 10 | 除了实现正确，还主动做了深度防御，没有可挑出的安全问题 |

### 5. Maintainability（可维护性）

| 分数 | 判定标准 |
|:---:|:---|
| 0 | 全是硬编码 + 全局变量 + 耦合，改一个点崩三个点 |
| 1–2 | 高度耦合，缺少分层，基本不可维护 |
| 3–4 | 有一点点分层，但一个函数做三件事、逻辑缠在一起 |
| 5–6 | 基本分层 OK，但模块边界模糊、依赖关系乱 |
| 7–8 | 职责清晰、依赖明确，改需求能快速定位修改点 |
| 9 | 模块化好、可插拔、易于扩展，配置集中管理 |
| 10 | 架构优雅、开闭原则落地、新人读 10 分钟就能上手改 |

### 6. Token Usage（Token 消耗，**越少越好**）

> 注：基准线 = 同任务「人类参考实现所需 Prompt + 输出 Token 的 1.2 倍」，记为 `T_ref`。实际消耗 = `T_actual`。

| 分数 | 判定标准 |
|:---:|:---|
| 0 | `T_actual` ≥ `T_ref × 5`（极度冗余） |
| 1–2 | `T_actual` 在 `T_ref × 3 ~ 5` 倍之间 |
| 3–4 | `T_actual` 在 `T_ref × 2 ~ 3` 倍之间 |
| 5–6 | `T_actual` 在 `T_ref × 1.5 ~ 2` 倍之间 |
| 7–8 | `T_actual` 在 `T_ref × 1.0 ~ 1.5` 倍之间 |
| 9 | `T_actual` 在 `T_ref × 0.8 ~ 1.0` 倍之间（比参考还省） |
| 10 | `T_actual` < `T_ref × 0.8`（非常高效，毫无废话） |

### 7. Latency（耗时，**越少越好**）

> 注：基准线 = 同任务「从 Prompt 发起到验收通过的参考耗时」，记为 `L_ref`。

| 分数 | 判定标准 |
|:---:|:---|
| 0 | 超时 / 实际 ≥ `L_ref × 10` |
| 1–2 | `L_actual` 在 `L_ref × 5 ~ 10` 倍之间 |
| 3–4 | `L_actual` 在 `L_ref × 3 ~ 5` 倍之间 |
| 5–6 | `L_actual` 在 `L_ref × 2 ~ 3` 倍之间 |
| 7–8 | `L_actual` 在 `L_ref × 1.2 ~ 2` 倍之间 |
| 9 | `L_actual` 在 `L_ref × 0.8 ~ 1.2` 倍之间 |
| 10 | `L_actual` < `L_ref × 0.8`（明显快于基准） |

### 8. Human Intervention（人工干预度，**越少越好**）

> 统计在完成任务过程中，人类做了多少次「纠错 / 重试提示 / 手动改代码 / 修复错误」的干预回合，记为 `H`。

| 分数 | 判定标准 |
|:---:|:---|
| 0 | `H ≥ 10`（基本上是人类自己写的，AI 只起了码字作用） |
| 1–2 | `H = 7 ~ 9` |
| 3–4 | `H = 4 ~ 6` |
| 5–6 | `H = 2 ~ 3` |
| 7–8 | `H = 1`（只需要一次小纠偏） |
| 9 | `H = 0`，但有 1 处明显瑕疵是验收时才发现的（无需干预即可修正） |
| 10 | `H = 0` 且一次性通过所有 AC（零返修） |

## 总分加权公式（V0.1 默认：**均权**）

V0.1 阶段我们先不偏向任何维度，8 个维度**权重相同**：

```
S_total = ( C + T + Q + Sec + M + Tok + Lat + H ) / 8
```

其中：

| 符号 | 维度 | 范围 |
|:---|:---|:---:|
| C   | Correctness         | 0-10 |
| T   | Test Pass Rate      | 0-10 |
| Q   | Code Quality        | 0-10 |
| Sec | Security            | 0-10 |
| M   | Maintainability     | 0-10 |
| Tok | Token Usage         | 0-10 |
| Lat | Latency             | 0-10 |
| H   | Human Intervention  | 0-10 |

得到的 `S_total` 也是 **0-10 分**，保留 2 位小数。

### 为什么 V0.1 用均权？

- 我们还不知道各维度在真实数据上的分布；
- 等 V0.2 跑出 10 个任务 × N 个模型的数据后，再根据实际差异调整权重；
- 调整权重时会在本文件顶部单独加一个「Changelog」章节，确保可追溯。

## 任务级打分如何落到维度分

每个任务的 `Evaluation` 节中会写：**每项 Acceptance Criterion 对应多少分、落到哪个维度**。举个通用例子（具体以每个任务文件为准）：

- "接口能返回 200" → 落到 **Correctness**，占 3 分
- "SQL 无注入" → 落到 **Security**，占 2 分
- "测试全通过" → 落到 **Test Pass Rate**，占 2 分
- …

最终每个维度的分 = 该维度下实际得分 ÷ 该维度下满分 × 10，再取整。
