# Task Planning（任务拆解）

## Purpose（目的）

把一个需求拆成"小步、可独立验证"的任务清单。每步范围受控，避免一个巨大 prompt 让 AI 一次写完一整个项目（那样必然出错、难调试）。

> 对应原则：**Small tasks over giant prompts（小任务胜过巨型提示）**。AI 一次只做一小步，做一步验一步。

## When to Use（何时使用）

- 需求/架构已定，准备开始编码
- 用户想把整个项目一次性丢给 AI
- 任务太大无法独立验证

## Trigger Conditions（触发条件）

- 用户说"帮我做完整个项目""一次性生成"
- 需求清单存在但还没有任务拆解
- 单个 prompt 输出过长/出错率高

## Preconditions（前置条件）

- 有需求清单或架构设计
- 已决定逐步推进（而非一把梭）

## Task Hierarchy（任务层级）

> 小白解释：就像盖房子——Epic 是"盖一栋楼"，Feature 是"做防水层"，Task 是"刷卫生间防水"，Subtask 是"买防水涂料"。越小越好验。

| 层级 | 大白话 | 示例 | 粒度 |
| --- | --- | --- | --- |
| Epic | 一个大模块 | "用户系统" | 1-4 周 |
| Feature | 一个可用的功能 | "用户注册登录" | 2-5 天 |
| Task | 一次可独立完成的操作 | "实现注册 API" | 半天以内 |
| Subtask | 一个操作的一个步骤 | "写密码加密逻辑" | 1-2 小时 |

**关键规则**：
- AI 直接执行的是 **Task 级**——太大（Feature）或太小（Subtask）都不合适。
- 一个 Task 必须能独立验收——做完能说"这条过了"或"这条没过"。
- 如果一个 Task 描述里出现"和"字（如"做登录和注册"），大概率要拆。

### 什么是好的 Task

一个合格的 Task 必须满足：

| 检查项 | 说明 | 示例 |
| --- | --- | --- |
| 范围明确 | 做什么、不做什么，边界清楚 | "完成用户注册 API，不含登录" |
| 输入明确 | 需要什么才能开始 | "需要 User 模型 + 路由框架已就绪" |
| 输出明确 | 做完产出什么 | "一个可调用的 POST /api/register 接口" |
| 文件范围明确 | 只改哪些文件 | "只改 routes/auth.js + controllers/auth.js" |
| 验收标准明确 | 怎么判定完成 | "正常注册返回 201 + 用户数据；重复注册返回 409" |
| 可独立测试 | 不依赖未完成的任务 | "可以单独跑接口验证" |

### 什么是坏的 Task

| 坏 Task | 为什么坏 | 怎么改 |
| --- | --- | --- |
| "把整个项目做好" | 无法验收、无法估时 | 拆成 Feature → Task |
| "做前端" | 范围太大 | 拆成"做笔记列表页""做编辑页" |
| "优化代码" | 没有验收标准 | 改成"把笔记查询从全量加载改为分页，每页 20 条" |
| "做登录和注册和找回密码" | 一个 Task 塞了 3 个功能 | 拆成 3 个 Task |

## Workflow（工作流）

1. **需求 → 拆子任务**：按模块/功能切。
2. **每任务 < 半天可完成**：粒度控制。
3. **标依赖顺序**：A 依赖 B 就排在 B 后。
4. **每任务配验收点**：做完怎么验。
5. **排成有序清单输出**：按依赖拓扑排序。

```mermaid
flowchart LR
    A[需求/架构] --> B[拆子任务]
    B --> C[控制粒度 <半天]
    C --> D[标依赖顺序]
    D --> E[每任务配验收点]
    E --> F[有序清单交付]
```

## Rules（规则）

- 单任务粒度要小（原则：Small tasks over giant prompts）。
- 每任务必须有验收标准。
- 有依赖要标（任务 B 依赖任务 A）。
- 清单按依赖拓扑排序，先做的排前面。
- 不在一个任务里塞多个不相关功能。
- 一个 Task 不出现"和"字——出现就拆。
- 每个 Task 必须满足 6 项检查（范围/输入/输出/文件范围/验收标准/可独立测试）。
- Subtask 只在 Task 确实复杂时才拆——不要为了拆而拆。

## Anti-Patterns（反模式）

- ❌ 一个任务"做完整个前端"
- ❌ 没有验收点，做完不知道对不对
- ❌ 不标依赖，导致顺序错乱
- ❌ 任务粒度过大（>半天）

## Validation（验证）

**Expected Validation Steps：**
1. 拿真实需求清单产出任务清单。
2. 检查每任务粒度 < 半天、有验收点、依赖已标。
3. 按清单顺序逐步执行，验证每步可独立通过验收。

## Output Format（输出格式）

| 序号 | 任务 | 依赖 | 验收点 |
|------|------|------|--------|
| 1 | … | - | … |
| 2 | … | 1 | … |
