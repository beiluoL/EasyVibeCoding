# Task Decomposition 拆任务

## 是什么

把一个大需求拆成若干个能独立完成、独立验证的小任务。大白话：别想着一口气盖一栋楼，先拆成"打地基、立柱、砌墙"，每步都能单独验收。

## 为什么重要

原则 02 Small tasks over giant prompts——大 Prompt 让 AI 一次干太多事，它容易顾此失彼、漏掉约束、产出超长且难验证。拆小后每步目标单一、上下文清晰、错了好回退。

拆任务也是给 Agent 的前置工作：Agent 自主跑的前提，是有清晰可判定的子目标。

## 怎么做

1. **从目标倒推**：要达成 X，需要先有 A、B、C
2. **每个任务满足"单次可完成 + 可独立验证"**：能在一个 Prompt/一个改动里做完，且有客观验收
3. **标依赖关系**：谁先谁后，哪些可并行
4. **每个任务配验收标准**：开工前就写清"做到什么算完成"（宪法第 6 条）
5. **粒度别太细**：太细变成微操作清单难维护，一个任务通常对应一个可提交的改动

相关技能：[`skills/core/task-planning`](../../skills/core/task-planning)。

## 常见错误

- **一个 Prompt 让 AI 写整个模块**：产出超长、难验证、错了一锅端。拆。
- **拆了任务不写验收标准**：做完说不清算不算好，违反宪法第 6 条。
- **任务之间依赖没理清**：并行跑了才发现 B 依赖 A 的产出，返工。
- **拆得太碎**：每个任务就改一行，管理成本比干活还高。

## 示例

需求："给订单列表加分页 + 按状态筛选"

| 拆法 | 任务 | 验收标准 | 依赖 |
| --- | --- | --- | --- |
| 错（一锅端） | 让 AI 一次写完 | "能跑" | 无 |
| 对（拆小） | T1 加分页参数和查询 | 默认返回第 1 页 20 条，total 正确 | 无 |
|  | T2 加状态筛选条件 | 选定状态只返回对应记录 | T1 |
|  | T3 接口联调 + 测试 | curl 能返回正确分页和筛选结果 | T1、T2 |

把这张表给 AI，它一次只做一个任务，每个都有明确验收。
