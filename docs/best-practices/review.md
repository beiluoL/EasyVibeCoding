# Review 结构化评审 AI 代码

## 是什么

用固定清单评审 AI 产出的代码，而不是"读一遍感觉还行就合"。大白话：拿一张检查表逐条对，别凭印象放行。

## 为什么重要

- **AI 代码常有隐性坑**：能跑但命名乱、和项目风格不符、有安全/性能隐患。
- **评审是合并前最后一道防线**：进主干后再发现代价翻倍。
- **结构化才不漏**：凭感觉评容易漏掉某一类问题，清单保证覆盖。

## 怎么做

按清单逐条过：

1. **正确性**：逻辑对不对？边界处理了吗？关键路径有测试吗
2. **一致性**：命名、分层、写法符合项目既有风格吗（原则 03）
3. **安全性**：有没有硬编码密钥、SQL 拼接、未校验输入、不安全的依赖
4. **性能**：有没有 N+1 查询、循环里干重活、不必要的全量加载
5. **可维护性**：是否过度设计、有没有死代码、注释是否说清"为什么"
6. **范围**：改动是否超出任务范围（顺手"优化"了不该碰的）
7. **验证**：测试跑了吗、有没有回归

对每条：通过 / 不通过（写明问题）。全过才合。

相关技能：[`skills/core/code-review`](../../skills/core/code-review)。

## 常见错误

- **"看起来挺好就合了"**：凭印象放行是评审最大的坑，用清单。
- **只看新代码不看影响面**：改一个公共方法可能影响所有调用方。
- **被 AI 的"自信"带跑**：AI 会用很确定的语气说"已优化"，仍要查证据。
- **评审范围太大**：一次评几百行谁也看不细。拆小、一次评一个任务（见 [task-decomposition](./task-decomposition.md)）。
- **只评功能不评安全**：安全漏洞常藏在"能跑"的代码里。

## 示例

评审清单（可直接用）：

| 维度 | 检查点 | 过/不过 |
| --- | --- | --- |
| 正确性 | 逻辑正确、边界覆盖、有测试 | ☐ |
| 一致性 | 命名/分层/风格符合项目规范 | ☐ |
| 安全性 | 无硬编码密钥、输入校验、安全依赖 | ☐ |
| 性能 | 无明显 N+1、无循环重活 | ☐ |
| 可维护性 | 无过度设计、无死代码 | ☐ |
| 范围 | 改动不越界、无顺手大改 | ☐ |
| 验证 | 测试通过、无回归 | ☐ |
