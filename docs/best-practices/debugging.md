# Debugging 系统化调试

## 是什么

按固定步骤找 Bug 的根因再修，而不是乱改碰运气。大白话：先能让 Bug 稳定复现，再一步步缩小范围定位到根因，最后才动手改。

这是宪法第 7 条 Every bug needs a reproducible cause 的落地。

## 为什么重要

- **乱改会引入新 Bug**：凭感觉改一处，可能压住表象但坏掉别处。
- **没复现就没法验证修复**：改完怎么知道真修好了？得能复现才能确认"不再出现"。
- **AI 尤爱"猜着改"**：它倾向快速给个看起来合理的改动，但常常没找到真因。

## 怎么做

1. **稳定复现**：找到一组确定能触发 Bug 的输入和步骤
2. **收集证据**：报错信息、日志、实际值 vs 期望值，都记下来
3. **缩小范围**：用注释/二分/日志定位到具体哪段代码、哪个分支
4. **定位根因**：别停在表象，问到"为什么会这样"的真正原因
5. **最小修复**：只改根因，不顺手"优化"别的（小步原则）
6. **验证修复**：复现原 Bug 确认不再出现 + 跑相关测试确认没回归
7. **沉淀知识**：这个坑记下来（见 [memory](../concepts/memory.md)），避免重蹈

相关技能：[`skills/core/systematic-debugging`](../../skills/core/systematic-debugging)。

## 常见错误

- **改了再看是不是好了**：本末倒置。先复现再定位再改。
- **只压表象不找根因**：加个 `if` 把异常吞掉，过几天换个姿势又犯。
- **修 Bug 顺手大改**：违反小步原则，一出问题不知道是修复还是改动引入的。
- **不验证就提交**：以为改了就行，没复现确认、没跑测试。
- **让 AI 直接"修这个 Bug"**：没给复现步骤和上下文，AI 只能猜着改。先给它证据。

## 示例

Bug：用户下单偶尔报"库存不足"但实际有库存。

错误做法：直接让 AI"修这个库存 Bug"——它可能加个重试了事。

系统化做法：

| 步骤 | 动作 | 产出 |
| --- | --- | --- |
| 1 复现 | 高并发下连续下单 | 稳定复现步骤 |
| 2 收集证据 | 看日志，发现扣减顺序乱了 | 并发竞态线索 |
| 3 缩小范围 | 定位到扣库存方法无锁 | 具体方法 |
| 4 根因 | 并发下读到旧库存 | 缺并发控制 |
| 5 最小修复 | 给扣减加乐观锁 | 只改这一处 |
| 6 验证 | 并发复现 + 单测 + 回归测试 | 确认修复且无回归 |
| 7 沉淀 | 记下"扣减类操作要加并发控制" | 知识 |
