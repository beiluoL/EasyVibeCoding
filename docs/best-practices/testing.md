# Testing 最小可验证测试

## 是什么

用最小的测试成本验证"这步到底对不对"。大白话：不靠"我觉得对了"，而是写个能自动跑、给"过/不过"明确结果的检查。

测试是原则 04 Evidence over claims 的主力证据来源。

## 为什么重要

- **AI 写的代码"看起来对"很多**：只有测试能给客观判定。
- **防回归**：今天改的功能明天被改坏，有测试立刻就知道。
- **让"完成"可判定**：宪法第 8 条要求每个任务都验证，测试是最省力的验证。

## 怎么做

1. **先定验收标准**：这步"对"的标准是什么，写成可检查的断言
2. **挑最小覆盖**：一个正常路径 + 一个边界 + 一个错误情况，够用即可
3. **能自动跑**：一条命令执行，输出"通过/失败"而非靠人看
4. **跑起来再说**：先让它红（失败），再让它绿（通过），避免"假绿"
5. **改动就跑**：每次改完跑相关测试，确认没回归

相关技能：[`skills/core/testing`](../../skills/core/testing)。

## 常见错误

- **只测"能跑"不测行为**：能启动 ≠ 功能对。要测实际输入输出。
- **AI 写测试 AI 自己跑"全绿"**：可能测试本身是空的或断言很弱。人看一眼断言是否真在检查。
- **测太多没用的**：覆盖一堆无关分支，维护成本高还找不到重点。先盖关键路径。
- **改完不跑测试**：测试写了不跑等于没写。
- **测试依赖环境/顺序**：换个机器或换顺序就挂，不可复现。

## 示例

验证"加法接口 `add(a,b)`"是否正确。

弱的验证：手输 `add(1,2)` 看到 `3` 就说对了。

最小可验证测试：

```java
// 正常路径
assertEquals(3, add(1, 2));
// 边界
assertEquals(0, add(0, 0));
// 错误情况（如负数按业务规则）
assertThrows(IllegalArgumentException.class, () -> add(-1, 2));
```

一条命令跑完，全绿才算这步对。改了 `add` 再跑，挂了立刻知道回归。
