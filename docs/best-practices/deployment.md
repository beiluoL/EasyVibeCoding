# Deployment 发布前检查与回滚

## 是什么

上线前用清单逐条确认 + 提前备好回滚方案。大白话：发版不是"点一下上线"，而是"按清单核对没漏 → 上 → 出问题能立刻退回去"。

## 为什么重要

- **上线是不可逆高危动作**：宪法第 9 条要求高风险动作必须人批准。
- **线上问题代价远大于开发期**：发版前花 10 分钟检查，省下线上几小时救火。
- **没回滚预案等于裸奔**：出问题现想怎么退，黄金时间就过了。

## 怎么做

发版前三步走：

1. **跑完发版检查清单**（见下方，对应 [`prompts/deployment/release-checklist.md`](../../prompts/deployment/release-checklist.md)）
2. **准备回滚方案**：怎么退、退到哪个版本、谁来执行、多久能退
3. **人审批后才发**：AI 不能自作主张发版（原则 05）

发版流程对应 [`workflows/release`](../../workflows/)。

## 发版检查清单

| 维度 | 检查点 |
| --- | --- |
| 代码 | 已通过评审、已合并到发版分支、无未提交冲突 |
| 测试 | 单元测试 + 关键集成测试全绿 |
| 构建 | 能干净构建、版本号已更新 |
| 配置 | 生产配置正确、密钥走环境变量不硬编码 |
| 数据 | 有没有数据库迁移、迁移可回滚 |
| 依赖 | 没引入未审查的新依赖 |
| 回滚 | 已备好回滚方案、回滚步骤验证过 |
| 通知 | 相关人知道这次发版内容和窗口 |
| 监控 | 上线后看哪些指标、异常谁响应 |

## 回滚预案

| 项 | 内容 |
| --- | --- |
| 触发条件 | 什么情况下立刻回滚（核心接口错误率超阈值、关键功能不可用） |
| 回滚方式 | 回退到上一版本镜像 / revert 代码合并 / 数据库迁移反向脚本 |
| 执行人 | 谁有权执行、谁复核 |
| 预计耗时 | 从决定回滚到生效多久 |
| 数据处理 | 回滚后产生的数据怎么办（保留/清理/迁移） |

## 常见错误

- **AI 说"可以发了"就发**：AI 没有判断线上风险的能力，必须人按清单核。
- **没回滚预案就上线**：出问题现找退路，常常退不干净。
- **数据库迁移不可逆**：删字段、改字段类型这种操作一旦执行退不回，要么分步做要么先备份。
- **发版即走人**：发完不看监控，问题到用户投诉才发现。留观察窗口。
- **跳过检查"小改一下没事"**：小改翻车的案例比比皆是，清单不分大小。

## 示例

一次小修复发版的最小流程：

| 步骤 | 动作 | 负责人 |
| --- | --- | --- |
| 1 | 跑发版检查清单，逐条打勾 | 开发 |
| 2 | 确认测试全绿、构建成功 | 开发 |
| 3 | 准备回滚：保留上一版本镜像、写回滚命令 | 开发 |
| 4 | 人审批发版 | 负责人 |
| 5 | 上线 | 开发 |
| 6 | 观察 30 分钟监控 | 开发+运维 |
| 7 | 异常则按预案回滚 | 开发 |
