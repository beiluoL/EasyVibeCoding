# RAG 检索失败

## Problem

做了一个 **RAG（检索增强生成：先从你的文档库里"搜相关片段"，再把搜到的内容喂给 AI 回答）** 知识库应用，用户问一个文档里明明写了的问题，AI 却答错了、或者干脆瞎编（幻觉）。查日志发现：压根没检索到正确的那段文档。

## Context

典型场景（示意）：小白开发者把 100 份产品手册 PDF 丢进 RAG 系统，**chunk size（切块大小：把长文档切成小段的长度）** 随便设成了 500 字，embedding（向量嵌入：把文字变成一串数字方便"相似度搜索"的过程，首次出现，配大白话：把文字翻译成机器能"比远近"的坐标）用了最便宜的模型，topK（每次检索取最相似的前几条）设了 3，也没做 rerank（重排：初筛之后再精细排序）。用户问："XX 型号打印机的废粉盒怎么换？"——答案明明在第 42 份手册的第 7 页，但检索只召回了 3 条不相关的"打印头清洗"内容，AI 基于错误的上下文开始编答案。

## Expected

用户提问后，RAG 系统能把包含正确答案的那一段文档排进前 3；AI 基于那段文档回答，并且引用来源可追溯（用户能点进去看原文哪一页写的）。

## Actual

检索召回的前几条都不包含正确答案，AI 拿到错误上下文后自然答不对；更糟糕的是回答看起来"很像那么回事"，用户一开始没发现，几天后才出问题。

## Root Cause

检索链路的 4 个关键环节至少有一个出问题：

1. **切块大小不对**：500 字一刀，把"废粉盒更换"一节切成了两块，答案被切散了，语义不完整，相似度就对不上。
2. **Embedding 模型不匹配**：用了英文通用 embedding 搜中文技术文档，"废粉盒"这种专业术语的向量质量差。
3. **TopK 太小**：只取前 3 条，正确答案排第 5，自然被丢掉。
4. **无重排（rerank）**：粗筛 embedding 相似度容易偏，缺一个精排步骤把真正相关的顶上去。

## Why AI Failed

RAG 是 **Garbage In, Garbage Out（垃圾进，垃圾出）** 的典型。检索错了，下游 LLM 再聪明也没用——**检索错 = 下游必错**，AI 没有办法"凭空知道"它没看到的文档内容。

同时，很多小白开发者误以为"只要东西进向量库就能搜到"，其实检索质量是要调的，不是一键到位。

## Fix

1. **调切块（chunking）**：
   - chunk size 改成 800~1200 字，加 10%~20% overlap（重叠），保证跨切块的内容不会被拦腰斩断。
   - 优先按标题/章节/段落的自然边界切，不要硬按字数切。
2. **换匹配的 Embedding 模型**：中文场景用中文专用 embedding（如 bge-large-zh、text-embedding-3-large 等），不要用英文通用模型。
3. **调 TopK + 加重排（rerank）**：
   - TopK 初筛放宽到 10~20（多捞几条，宁滥勿缺）。
   - 然后用 rerank 模型（如 bge-reranker、Cohere rerank 3）做精排，只留前 3~5 条给 LLM。
4. **引用来源可追溯**：AI 的每个回答都必须附带"引用了哪些 chunk 的哪份文档第几页"，用户一眼就能核对，也方便排查"是不是没召回对"。
5. **加检索校验**：如果检索结果的相似度分数低于阈值（比如 0.6），直接告诉用户"没找到相关内容"，别瞎编。

## Prevention

- 在 [rag 技能](../../skills/ai/rag/SKILL.md) 里对照"RAG 常见错误清单"过一遍：切块、Embedding、TopK、Rerank、引用追溯、低分兜底。
- 做 RAG 上线前一定要先跑 **评测集**：准备 20~50 个你关心的"标准问答对"，每改一个参数就跑一遍看命中率，别凭感觉调。
- 每次用户反馈答不对，第一反应不是骂 AI 笨，而是先看日志：**检索召回的那几条到底对不对？** 90% 的情况问题出在检索，不在生成。
- 不要一拍脑袋定架构（比如直接说"就用 RAG"），先做小实验验证。相关反模式参见：[architecture-by-guessing](../../anti-patterns/architecture-by-guessing.md)。
