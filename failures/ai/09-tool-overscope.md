# Tool 权限过大

## Problem

为了"让 AI 做事方便"，一次性给了它一堆强力工具：能删任意文件、能发任意 HTTP 请求、能连生产数据库执行 SQL、能调用公司内部 API 发群消息。结果 AI 一次误操作（比如误解了"清理"的意思，把 `src/` 目录当成临时文件删了；或者把调试消息发到了全员大群），直接造成经济损失或社死。

## Context

典型场景 1（示意）：开发者给 AI Agent 配了 `delete_files` 工具，没做路径限制，也没加确认。任务是："清理 build 目录里的临时文件"。AI 理解成了"清理项目中所有看起来像临时文件的东西"，结果匹配了一个过宽的 `**/*.tmp` 模式后，又因为一个参数错误把 `src/` 下的几个 `.tsx` 文件当成匹配项删了，还没走回收站。代码没提交 git，半天的工作没了。

典型场景 2（示意）：AI 集成了 MCP（Model Context Protocol：AI 和外部工具通信的标准协议，首次出现，配大白话：让 AI 能安全调用各种外部工具的通用插座）里的飞书消息工具，权限是"可向任意群、任意人发任意消息"，也没加确认。AI 在调试过程中把一条包含大量错误日志的"测试消息"，误发到了 500 人的全公司大群。

## Expected

每个工具都遵守**最小权限原则**（只给它刚好够用的权限，多一点都不给）；凡是高危工具（删文件、写生产库、发外部消息、付款……）必须先让人类确认才能执行。

## Actual

工具"一把梭"全给了，也没分层，结果：

- AI 的一个小误解，变成了真实的破坏性操作。
- 误删/误发/误改，不可逆。
- 事后追责时发现"根本没日志"，因为工具调用也没加审计。

## Root Cause

两个核心错误：

1. **工具权限未最小化**：`delete_files` 本应限制在 `build/` 目录，实际给了根目录；飞书发消息本应限制在"测试群"，实际给了"全部群"。
2. **高危操作无确认机制**：删文件、生产 DB 写操作、发外部消息这类**不可逆操作**，缺少"执行前弹出给人类二次确认"的环节。

加上开发者的心态："先跑起来再说，安全之后再加"——然后就忘了。

## Why AI Failed

AI 不懂什么叫"危险"。它只是按指令完成任务，在它眼里：

- 删 `build/` 下的 `.tmp` 和删 `src/` 下的 `.tsx`，都是"调用 delete_files 工具传一个路径列表"。
- 发消息到"测试群"和发消息到"全员大群"，都是"调用 send_message 传一个 chat_id"。

AI 没有"这个操作出事会很尴尬/很费钱"的常识，除非你在工具层**硬加**限制和确认，否则它不会自己停下来。

## Fix

1. **做权限白名单，分三档**：
   - **Auto（自动执行）**：低风险工具，只读不写。例：`read_file`、`grep_search`、`list_dir`、`curl -X GET`（只读 API）。AI 可以随便用。
   - **Confirm（需确认）**：有副作用、不可逆的操作。例：`delete_file`、`write_file`（涉及覆盖）、`run_command`（非 dry-run）、发送任何对外消息、调用付款 API、任何生产库的写 SQL。**必须先弹给人类看，点"确认"再执行**。
   - **Deny（禁止）**：完全不给的能力。例：`rm -rf /`、生产库 `DROP TABLE`、向非白名单 chat_id 发消息、超过 $100 的单笔付款。
2. **参数白名单 / 范围限制**：
   - `delete_files` 只允许 `build/`、`dist/`、`tmp/` 三个目录路径，其他路径直接拒绝。
   - 飞书消息工具：`chat_id` 必须在白名单（2~3 个测试群），其他一律拒绝。
   - DB 工具：非 `SELECT` 语句默认只能连 `localhost` / test 库，生产库写操作需要额外的授权 header。
3. **加 dry-run 模式**：所有高危工具支持"先模拟执行、显示影响范围、等确认再真做"。例：`delete_files --dry-run` 先列出来会删哪些文件，条数>5 时红色警告。
4. **加工具调用审计日志**：每次调用谁、调了什么工具、什么参数、返回什么、谁确认的，全部写进日志文件，方便事后排查。

## Prevention

- 配工具时按 [tool-calling 技能](../../skills/ai/tool-calling/SKILL.md) 的安全清单一条条过：**每个工具都要回答"最坏情况是什么？防了吗？"**。
- MCP 接入外部服务时，参照 [mcp 技能](../../skills/ai/mcp/SKILL.md) 的"安全边界设计"一节：MCP 只是"插座"，插座前面必须装**保险丝（权限）+ 漏保（确认）+ 电表（审计）**。
- 首次接入一个新工具，**先在 Confirm 档跑至少 20 次**，确认副作用在预期内，再考虑降级到 Auto。反过来绝不要：先 Auto，出事了再改 Confirm。
- 生产环境的工具默认走 Confirm，测试环境可以放宽。**别把测试环境的配置直接抄到生产**。
