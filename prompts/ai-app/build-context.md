# 构建上下文（build-context）

## Use When（何时使用）

> AI 某一步行为不稳定或答非所问，需要从"该让它看到哪些信息"入手，设计上下文组装方案。

## Goal（目标）

> 针对指定步骤，决定 AI 该看到哪些信息：选（取哪些）→ 压（精简）→ 排（顺序）→ 丢（舍弃），给出可落地的上下文组装方案。

## Input Variables（输入变量）

- `{{task_step}}`：要设计上下文的具体步骤（如：生成回复、调用工具前）。
- `{{available_info}}`：候选可用信息（用户输入、历史、检索片段、工具说明等）。
- `{{token_budget}}`：上下文预算（大致可用 token 数）。

## Prompt（提示词正文）

```
Role: 你是一名上下文工程师，信奉"模型行为不稳定八成是上下文没喂对"。
Context: 步骤：{{task_step}}
候选信息：{{available_info}}
token 预算：{{token_budget}}
Goal: 给出该步骤的上下文组装方案：选 → 压 → 排 → 丢。
Constraints:
- 必须分四步给方案：
  1. 选：从 {{available_info}} 里取哪些，说明为什么取、为什么不取。
  2. 压：哪些可精简（摘要/去噪/截断），压缩到多少。
  3. 排：信息在 prompt 里的顺序（系统指令/示例/检索片段/用户输入如何排）。
  4. 丢：哪些必须舍弃（敏感、过期、与任务无关）。
- 必须给出最终拼好的 prompt 模板，含占位符。
- 必须说明"为什么这么排"的依据（如：指令在前模型更遵循、相关片段靠近问题更易利用）。
- 控制在 {{token_budget}} 内，超出要说明砍哪里。
- 未实测效果，标注 ⚠️ Not Yet Verified，建议用 A/B 对比验证。
Workflow:
1. 列出候选信息并标注相关度。
2. 按四步给出处理决策。
3. 输出最终 prompt 模板。
4. 给出验证建议。
Output format:
## 选/压/排/丢 决策表
## 最终 prompt 模板
## 排序依据
## ⚠️ 未验证与验证建议
Verification: 回顾是否四步齐全、是否有最终模板、排序是否有依据、是否在预算内、是否诚实标注未验证。
```

## Expected Behavior（期望行为）

> 模型按选/压/排/丢四步给出决策，输出可落地 prompt 模板，排序有依据，控制预算，诚实标注未验证。

## Expected Output（期望输出）

```
## 选/压/排/丢
选：系统指令+检索top3+用户输入（舍历史闲聊）
压：历史摘要到1句
排：系统指令→示例→检索片段→用户输入
丢：敏感字段、过期事实
## 最终模板
[系统指令] + [示例] + [检索片段] + [用户输入]
## 排序依据
指令在前更被遵循；片段靠近问题更易利用
## ⚠️ 未验证
建议 A/B 对比当前与新版输出质量
```

## Validation（验证）

- 选/压/排/丢四步都有决策。
- 有最终 prompt 模板。
- 排序有依据，控制在预算内。

## Common Mistakes（常见错误）

- 把所有候选信息都塞进去，超预算还稀释重点，模型反而更糊涂。
- 不排顺序，系统指令混在用户输入后面，模型不遵循。
- 不丢过期/敏感信息，导致用错事实或泄露隐私。
- 不给验证建议，改完不知道好没好。
