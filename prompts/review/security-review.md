# 安全审查（security-review）

## Use When（何时使用）

> 功能代码要上线前，做一次专项安全检查，专门盯注入、XSS、鉴权、密钥泄露、依赖漏洞这几类高频风险。

## Goal（目标）

> 对代码做专项安全审查，逐类排查常见漏洞，发现即按 blocker/warn 分级，给出位置、攻击场景与修复建议。

## Input Variables（输入变量）

- `{{code_diff}}`：待审查的代码变更。
- `{{auth_model}}`：本功能的鉴权模型说明（谁能访问、如何鉴权），可选但强烈建议提供。

## Prompt（提示词正文）

```
Role: 你是一名安全审查者，假设代码会被恶意用户主动攻击，而不是按正常流程使用。
Context: 待审查代码：
{{code_diff}}
鉴权模型：{{auth_model}}
Goal: 逐类排查以下安全风险，发现即输出 blocker/warn + 位置 + 攻击场景 + 修复建议。
Constraints:
- 必须逐类检查，无相关也要标注"未发现/不适用"，不能整类跳过：
  1. 注入：SQL 拼接、命令注入、模板注入、NoSQL 注入。
  2. XSS：用户输入是否未转义就回显到页面/属性/脚本。
  3. 鉴权与越权：是否校验身份、是否校验"对这个资源的权限"（不只是登录态）。
  4. 密钥与敏感信息泄露：硬编码密钥/Token、日志打印密码、错误信息泄露堆栈。
  5. 依赖漏洞：是否引入已知有漏洞的依赖版本。
- 每个发现给出具体攻击场景（攻击者会怎么利用），而不是只说"不安全"。
- 修复建议要可落地，给出具体替代写法。
- 你没有实际做渗透测试，发现基于代码静态分析，标注 ⚠️ Not Yet Verified，建议运行时再验证。
Workflow:
1. 通读代码，标记所有"用户可控输入"的入口。
2. 追踪每个输入到使用点，检查是否被安全处理。
3. 检查每个鉴权/授权判断点是否覆盖到位。
4. 扫描密钥硬编码与日志输出。
5. 汇总发现并分级。
Output format:
| 类别 | 级别 | 位置 | 攻击场景 | 修复建议 |
最终结论：是否存在 blocker 级安全问题。
Verification: 回顾是否每类都留痕、每个发现是否有攻击场景而非笼统"不安全"、修复建议是否可落地。
```

## Expected Behavior（期望行为）

> 模型以"攻击者视角"逐类排查，给出攻击场景和可落地修复，无发现的类别也留痕，不假设安全。

## Expected Output（期望输出）

```
| 类别 | 级别 | 位置 | 攻击场景 | 修复建议 |
| 注入 | blocker | search.js:9 | 拼接 SQL，攻击者可注入 ' OR 1=1 | 参数化查询 |
| XSS | warn | profile.js:23 | 用户昵称未转义直染，可注入 <script> | 输出转义或框架自动转义 |
| 鉴权 | blocker | order.js:30 | 只查登录态，未校验订单归属，可越权他人订单 | 加 owner 校验 |
| 密钥泄露 | 未发现 | — | — | — |
| 依赖漏洞 | ⚠️ Not Yet Verified | 未做依赖扫描 | — | 跑 npm audit / safety |
最终结论：存在 2 个 blocker，不可上线。
```

## Validation（验证）

- 5 类风险全部留痕（含"未发现"）。
- 每个发现都有具体攻击场景。
- blocker 级问题有可落地修复建议。

## Common Mistakes（常见错误）

- 只检查"有没有登录"，漏掉"有没有权限操作这个具体资源"（水平越权）。
- 发现问题只说"不安全"不说攻击者怎么利用，评审无法判断严重度。
- 只看代码不做依赖扫描，漏掉第三方库已知漏洞。
- 把 SQL 注入这种 blocker 标成 nit 放行。
