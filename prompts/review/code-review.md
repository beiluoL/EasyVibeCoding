# 代码审查（code-review）⭐

## Use When（何时使用）

> AI 生成了代码，你要判断它能不能合入主干。不能凭"读着挺顺"就放行，要过一遍结构化清单再下结论。

## Goal（目标）

> 用至少 7 项的结构化清单评审代码，每条问题标注 blocker/warn/nit，给出 位置+理由+建议，最后给出明确合入结论。

## Input Variables（输入变量）

- `{{code_diff}}`：待评审的代码变更（diff 或完整代码）。
- `{{acceptance_criteria}}`：本次变更应满足的验收标准。

## Prompt（提示词正文）

```
Role: 你是一名资深代码评审者，对合入主干负责。你的目标不是挑刺，而是挡住会出事、难维护的代码。
Context: 以下是待评审的代码变更：
{{code_diff}}
它声称满足的验收标准是：
{{acceptance_criteria}}
Goal: 用结构化清单逐项检查，输出问题清单（blocker/warn/nit + 位置 + 理由 + 建议），最后给出合入结论。
Constraints:
- 禁止只说"代码没问题""写得不错"就放行——必须逐项过清单并留痕。
- 至少过以下 7 项清单（无相关的也要标注"不适用"并说明原因，不能跳过）：
  1. 是否满足全部 {{acceptance_criteria}}。
  2. 错误处理是否完整（异常分支、空值、失败回退）。
  3. 是否存在硬编码密钥、Token、连接串。
  4. 是否存在注入风险（SQL 拼接、命令注入、XSS 未转义）。
  5. 是否有明显重复代码或可抽取的公共逻辑。
  6. 命名是否表达意图（变量/函数/文件名是否需要猜）。
  7. 是否附带测试，测试是否覆盖正常/边界/错误路径。
- 问题分级：blocker=不可合入；warn=可合但需跟进；nit=建议优化。
- 每条问题给：文件:行号、为什么是问题、怎么改。
- 没有实际运行验证的部分，标注 ⚠️ Not Yet Verified，不假设它工作。
Workflow:
1. 先对照 {{acceptance_criteria}} 确认变更是否覆盖全部需求点。
2. 逐项过 7 项清单，记录发现。
3. 按严重度分级汇总问题。
4. 给出合入结论：可合入 / 需修改后合入 / 不可合入。
Output format:
## 清单逐项
1. 满足验收：✅/❌/⚠️ + 说明
...（7 项）
## 问题清单
| 级别 | 位置 | 问题 | 理由 | 建议 |
## 合入结论
可合入 / 需修改后合入 / 不可合入 + 关键阻塞项
Verification: 回顾是否每项清单都留痕（含"不适用"说明）、每个 blocker 是否有位置与修复建议、结论是否与问题清单一致。
```

## Expected Behavior（期望行为）

> 模型应扮演资深评审者，逐项过清单、按级分类问题、给出位置与建议，最后下二值化的合入结论，不放无依据的"绿灯"。

## Expected Output（期望输出）

```
## 清单逐项
1. 满足验收：✅ 三条标准都有对应实现
2. 错误处理：❌ 未捕获 fetch 网络异常
3. 硬编码密钥：✅ 无
4. 注入风险：❌ 用字符串拼接 SQL
5. 重复代码：✅ 无明显重复
6. 命名：✅ 表达清晰
7. 测试：⚠️ 仅有正常路径，缺边界
## 问题清单
| 级别 | 位置 | 问题 | 理由 | 建议 |
| blocker | user.js:42 | SQL 拼接 | 注入风险 | 改用参数化查询 |
| blocker | user.js:18 | 未处理网络异常 | 失败会崩 | 加 try/catch + 回退 |
| nit | user.js:5 | magic number 5 | 含义不明 | 提为常量 MAX_RETRY |
## 合入结论
不可合入。阻塞项：SQL 注入、未处理网络异常。
```

## Validation（验证）

- 7 项清单全部出现且每项有判定（含"不适用"说明）。
- 每个 blocker 都有位置 + 理由 + 建议。
- 合入结论与问题清单一致（有 blocker 就不是"可合入"）。

## Common Mistakes（常见错误）

- 只说"代码没问题"就放行，没逐项过清单，把评审变成橡皮图章。
- 问题只说"这里有点问题"不给位置和改法，开发无从下手。
- 把 blocker（SQL 注入、未处理异常）降级成 nit 放过去。
- 只评"代码风格"不评"是否满足验收标准"，本末倒置。
