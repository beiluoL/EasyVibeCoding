# 性能审查（performance-review）

## Use When（何时使用）

> 功能跑得通但担心慢，需要专项找出性能瓶颈（N+1、全表扫、无缓存、重复计算）并给出优化方向。

## Goal（目标）

> 识别代码中的性能瓶颈，按影响分级，给出优化建议和"预期改善方向"——但不编造具体数字指标。

## Input Variables（输入变量）

- `{{code_diff}}`：待审查的代码。
- `{{scale_context}}`：预期数据量与访问量（如：用户表 10 万行、QPS 约 50），用于判断瓶颈严重度。

## Prompt（提示词正文）

```
Role: 你是一名注重"用最小改动拿到最大收益"的性能审查者，不追求过早优化。
Context: 待审查代码：
{{code_diff}}
规模上下文：{{scale_context}}
Goal: 找出真实瓶颈并分级，给出优化建议和预期改善方向，不编造性能数字。
Constraints:
- 逐类排查以下高频瓶颈，无相关也要标注"未发现"：
  1. N+1 查询：循环里发起数据库/外部请求。
  2. 全表扫描：查询未走索引、LIKE 前缀通配、函数包裹索引列。
  3. 无缓存：重复请求相同数据且可缓存。
  4. 重复计算：循环内反复算可提前算好的值。
  5. 阻塞调用：在请求路径里做同步 IO/远程调用。
- 分级：high=影响主路径或大数据量；medium=中等影响；low=优化余地小。
- 每条给：位置、为什么慢、优化建议、预期方向（如"减少 N 次查询到 1 次"）。
- 严禁编造"提速 3 倍""延迟降到 5ms"等未经测量的数字；未实测标注 ⚠️ Not Yet Verified。
- 不要为不存在的瓶颈建议过度优化（如数据量才几十行就建议加缓存）。
Workflow:
1. 标记代码中的循环、数据库查询、外部调用位置。
2. 对照 {{scale_context}} 判断每处是否会成为瓶颈。
3. 给出优化建议与预期方向。
4. 汇总分级清单。
Output format:
| 瓶颈类型 | 级别 | 位置 | 为什么慢 | 优化建议 | 预期方向 |
Verification: 回顾是否每条都有"为什么慢"而非笼统"性能差"、预期方向是否定性而非编造数字、是否结合规模判断严重度。
```

## Expected Behavior（期望行为）

> 模型结合数据规模判断瓶颈是否真实，给出定性优化方向，不编造性能数字，不为小数据量过度优化。

## Expected Output（期望输出）

```
| 瓶颈类型 | 级别 | 位置 | 为什么慢 | 优化建议 | 预期方向 |
| N+1 查询 | high | order.js:25 | 循环内逐条查用户 | 批量 IN 查询或 JOIN | N 次查询 → 1 次 |
| 无缓存 | medium | config.js:8 | 每次请求重读配置 | 进程内缓存配置 | 每请求1次IO → 启动1次 |
| 全表扫描 | low | search.js:40 | LIKE '%x' 前缀通配 | 改全文索引或限定前缀 | 视数据量决定 |
（未实测，⚠️ Not Yet Verified，建议实测前后对比）
```

## Validation（验证）

- 每条瓶颈都有"为什么慢"的具体解释。
- 优化建议是定性方向，无编造的提速数字。
- 严重度结合 {{scale_context}} 判断，没有为小数据量建议过度优化。

## Common Mistakes（常见错误）

- 编造"提速 3 倍""延迟降到 5ms"等未测过的数字，误导决策。
- 不看数据量就建议加缓存加索引，给几十行数据也上缓存。
- 只说"性能差"不说哪慢、为什么慢，无法定位。
- 把"循环里查数据库"这种 high 瓶颈漏掉，只挑格式小问题。
