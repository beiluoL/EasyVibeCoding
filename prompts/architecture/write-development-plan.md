# write-development-plan
## Use When
需求和架构都定了，但还没排"先做什么后做什么、每个任务多大、谁依赖谁"。直接开干会乱套、返工、卡在等依赖上。

## Goal
把需求拆成有序、可独立验证的任务清单：每个任务 < 半天、有验收点、标了依赖关系。让一个新人照着清单一天一天做下去就能把项目做完。

## Input Variables
- `{{requirement_list}}`：上一阶段的 FR/NFR 清单。
- `{{architecture}}`：上一阶段的技术架构（模块图 + 数据模型）。
- `{{team_size}}`（可选）：多少人做，影响并行度。

## Prompt
```
你是一位资深技术负责人，擅长把"需求 + 架构"拆成开发能一天天推进的任务清单。

【角色 Role】资深技术负责人
【背景 Context】用户有需求清单 {{requirement_list}} 和架构 {{architecture}}，团队规模 {{team_size}}。需要把"要做什么"拆成"按什么顺序做、每步多大、怎么验证做完"。
【目标 Goal】产出一份带优先级和依赖的任务清单，每个任务 < 半天，能独立验证，标了依赖关系。
【约束 Constraints】
1. 每个任务必须 < 半天（4 小时），超出就继续拆。
2. 每个任务必须有"验收点"（做完能跑什么验证）。
3. 必须标依赖（任务 B 依赖 A，A 没做完 B 不能开始）。
4. 优先级用 P0/P1/P2，P0 是"不做项目跑不起来"。
5. 大白话，术语第一次出现配解释。
6. 不写代码实现，只写任务描述。
7. 给一个"关键路径"（最长的依赖链，决定项目最快多久能做完）。
【工作流 Workflow】
1. 从 FR 抽出"用户能做的事"，每个再拆成前后端 / 数据子任务。
2. 给每个任务标大小、验收点、依赖。
3. 按依赖排顺序，找关键路径。
4. 标优先级。
5. 输出任务表 + 关键路径 + 总工期估算。
【输出格式 Output Format】
# 开发任务清单

## 任务表
| ID | 任务 | 大小 | 依赖 | 优先级 | 验收点 |
| --- | --- | --- | --- | --- | --- |
| T-001 | 建数据表 schema | 1h | - | P0 | 跑 migrate 不报错，表里有字段 |
| T-002 | 写录入接口 | 3h | T-001 | P0 | curl 提交，DB 里出现记录 |

## 关键路径
T-001 → T-002 → T-004 → T-007（共 X 小时 = Y 天）

## 总工期估算
<一句话>
【验证 Verification】
- 每个任务是否 < 半天？超出的拆了吗？
- 每个任务是否有验收点？
- 依赖是否画清了？有没有循环依赖？
- 关键路径是否标出来了？
```

## Expected Behavior
- 任务粒度严格 < 半天，超出自动拆。
- 每个任务都有"做完能跑什么"的验收点。
- 依赖清晰，能识别关键路径。
- 不写实现代码，只描述任务。

## Expected Output
（示例片段）
```
## 任务表
| ID | 任务 | 大小 | 依赖 | 优先级 | 验收点 |
| --- | --- | --- | --- | --- | --- |
| T-001 | 建房租表 schema（id/amount/due_date/paid） | 1h | - | P0 | migrate 成功，desc 表能看到字段 |
| T-002 | 写录入接口 POST /rent | 3h | T-001 | P0 | curl 提交，DB 出现一条 |
| T-003 | 前端录入表单 | 3h | T-002 | P0 | 填表提交，列表出现这条 |
| T-004 | 到期检测定时任务 | 2h | T-001 | P0 | 手动改 due_date 为今天+3，跑任务，日志打印"提醒" |

## 关键路径
T-001 → T-002 → T-003 → T-004（共 9h ≈ 1.5 天）

## 总工期估算
按 P0 算约 1.5 天，加 P1 约 3 天。
```

## Common Mistakes
1. 任务粒度太大（"做完前端"3 天），没法验收中间进度。
2. 不标依赖，开发做到一半发现卡在别人没做完的任务上。
3. 验收点写成"做完就行"，没说跑什么、看什么。
4. 不找关键路径，并行机会被浪费，工期拖长。
