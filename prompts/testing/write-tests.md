# 编写测试（write-tests）

## Use When（何时使用）

> 功能代码刚写完，需要给它配一套"最小可验证测试"，让"是否完成"有客观依据，而不是靠肉眼判断"看着像没问题"。

## Goal（目标）

> 为指定功能编写覆盖正常路径、边界路径、错误路径的最小测试集，每条用例都映射到一条验收标准。

## Input Variables（输入变量）

- `{{feature}}`：功能名称与简要描述（要测什么）。
- `{{acceptance_criteria}}`：该功能的验收标准清单（每条要可验证）。

## Prompt（提示词正文）

```
Role: 你是一名注重"先验证再交付"的测试工程师。
Context: 功能 {{feature}} 已经实现，对应的验收标准如下：
{{acceptance_criteria}}
我需要的是一套最小但可自动验证的测试，而不是追求覆盖率数字。
Goal: 为 {{feature}} 编写测试用例，覆盖三类路径——正常路径、边界路径、错误路径，每条用例都标注它验证的是哪一条验收标准。
Constraints:
- 每条用例必须能独立运行，不依赖执行顺序。
- 用例名要表达意图，例如 test_空字符串时返回400，而不是 test_case_1。
- 边界路径要给出具体的边界值，例如空、单个、最大长度、临界点正负一。
- 错误路径要明确触发什么异常/状态码，而不是笼统说"出错"。
- 不要为"不可能发生"的内部调用造测试，只测对外契约。
- 不要伪造运行结果；没有实际跑过的用例标注 ⚠️ Not Yet Verified。
Workflow:
1. 把 {{acceptance_criteria}} 每条拆成一条或多条可观察的断言。
2. 为每条断言设计正常路径用例（期望成功）。
3. 在每个临界值上设计边界路径用例。
4. 为非法输入、权限不足、依赖失败设计错误路径用例。
5. 输出可直接落地的测试代码骨架，含必要注释。
Output format: 用下表列出每条用例，随后给出代码骨架：
| 用例名 | 路径 | 验证标准 | 输入 | 期望输出 |
Verification: 回顾三类路径是否齐全、每条用例是否都能映射到一条验收标准、是否存在只测实现细节而非行为的用例；如有未实际运行的用例，明确标注。
```

## Expected Behavior（期望行为）

> 模型应先逐条对应验收标准，再分三类路径列用例，最后给出可落地的代码骨架，并对未跑过的用例诚实标注。

## Expected Output（期望输出）

```
| 用例名 | 路径 | 验证标准 | 输入 | 期望输出 |
| test_合法邮箱注册成功 | 正常 | AC1 | email=a@b.com | 201, 返回 user_id |
| test_邮箱恰好254字符 | 边界 | AC1 | email=(254字符) | 201 |
| test_邮箱255字符 | 边界 | AC1 | email=(255字符) | 400 |
| test_邮箱格式错误 | 错误 | AC2 | email=abc | 400 |
（随后给出对应测试代码骨架，未运行用例标注 ⚠️ Not Yet Verified）
```

## Validation（验证）

- 每条验收标准至少有一条用例覆盖。
- 三类路径（正常/边界/错误）都出现。
- 用例名表达意图而非编号。
- 未实际运行的用例已标注 ⚠️ Not Yet Verified，不谎称通过。

## Common Mistakes（常见错误）

- 只写正常路径，漏掉边界和错误路径，导致"看起来全绿其实没覆盖风险点"。
- 追求覆盖率数字，写出测实现细节而非行为的用例，一重构就崩。
- 用例之间互相依赖执行顺序，单独跑就失败。
- 用例名用 test_1/test_2，看不出意图，失败时不知道哪条业务规则挂了。
