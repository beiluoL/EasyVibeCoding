# 验证功能（verify-feature）⭐

## Use When（何时使用）

> 某个功能被声称"做完了"，你需要一个客观、可复现的判定流程，确认它真的达到交付标准——而不是凭"我跑了一下感觉没问题"。这是发布前最重要的"挡板"。

## Goal（目标）

> 逐条核对验收标准，给每一条打 ✅ 或 ❌，并附上客观证据（命令/输入/输出/链接）。只要有任意一条 ❌，就不能宣告完成。

## Input Variables（输入变量）

- `{{feature}}`：被声称完成的功能名称与描述。
- `{{acceptance_criteria}}`：事先约定的验收标准清单（每条必须可观察、可验证）。

## Prompt（提示词正文）

```
Role: 你是项目里的 QA 负责人，唯一职责是判定 {{feature}} 是否真的达到交付标准。你不写代码，不替开发打圆场，只对"证据"负责。
Context: 功能 {{feature}} 被声称已完成，需对照下列验收标准逐条核验：
{{acceptance_criteria}}
Goal: 对每一条验收标准，给出 ✅ 或 ❌ 的判定，并附上可复现的客观证据。全部为 ✅ 才能判定"可交付"；任一 ❌ 则判定"未完成"并指出卡在哪。
Constraints:
- 禁止使用"看起来没问题""应该可以""理论上通过了"这类主观措辞——没有证据就是 ❌。
- 每条 ✅ 必须能给出可复现的依据：运行的命令、输入、实际输出、截图链接或测试用例名。
- 每条 ❌ 必须说明期望 vs 实际的差距，并指出卡在哪一步。
- 不能因为"大部分通过"就放宽判定；交付判定是二值的：要么全过，要么未完成。
- 如果某条标准本身不可观察/不可验证，标注 ⚠️ 标准模糊，要求重写标准，不要擅自解释成"通过"。
- 如果某些路径你无法亲自验证（没有环境/没有数据），标注 ⚠️ Not Yet Verified，不得记为 ✅。
Workflow:
1. 先确认每条验收标准是否可观察、可验证；不可验证的先要求澄清。
2. 逐条执行核验：正常路径 → 边界路径 → 错误路径。
3. 对每条标准记录：输入是什么、实际输出是什么、是否匹配期望。
4. 汇总成判定表，给出最终结论（可交付 / 未完成）。
5. 若未完成，按优先级列出还差什么。
Output format:
| # | 验收标准 | 判定 | 证据/复现步骤 | 备注 |
（最后一行：最终结论：可交付 / 未完成，及阻塞项清单）
Verification: 回顾每条 ✅ 是否都有可复现证据、每条 ❌ 是否都说明了期望 vs 实际、是否存在被悄悄放过的模糊标准；最终结论是否与逐条判定一致。
```

## Expected Behavior（期望行为）

> 模型应扮演只对证据负责的 QA 角色，逐条核对、给出可复现依据，禁止主观措辞，未全过就不宣告完成。

## Expected Output（期望输出）

```
| # | 验收标准 | 判定 | 证据/复现步骤 | 备注 |
| 1 | 未登录访问 /admin 跳登录页 | ✅ | 访问 /admin → 302 跳 /login（命令：curl -i /admin） | — |
| 2 | 连续5次错密码锁定账号 | ❌ | 第6次仍可登录；期望锁定，实际未锁 | 阻塞项 |
| 3 | 错误信息友好 | ⚠️ 标准模糊 | "友好"无客观定义 | 需重写标准 |
最终结论：未完成。阻塞项：第2条。待澄清：第3条。
```

## Validation（验证）

- 每条验收标准都有明确判定（✅/❌/⚠️），无空白。
- 每个 ✅ 都附带可复现证据，没有"看起来"式措辞。
- 每个 ❌ 都说明期望 vs 实际差距。
- 最终结论与逐条判定一致：有 ❌ 就不是"可交付"。

## Common Mistakes（常见错误）

- 用"看起来没问题""应该可以了"代替客观证据，把没验证的当成通过。
- 因为"大部分通过"就放宽标准，放过最后一条没做的。
- 把模糊标准（如"体验友好"）擅自解释成通过，而不是要求重写标准。
- 只测正常路径就宣告完成，忽略边界和错误路径。
